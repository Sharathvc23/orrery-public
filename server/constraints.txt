#
# sm-bridge 0.10.0 (from 0.6.0): takes the 0.7.0 SECURITY fix, which 0.6.0 predates.
# 0.7.0 anchored /nanda/resolve: an identifier scoped to a DIFFERENT registry
# (@other:ns/foo, or a did:web under another host) was reduced to a bare id and
# answered locally, carrying THIS registry's proof block, with nothing telling the
# caller the scope had been ignored. Orrery is multi-tenant and mounts that router
# at /sm-bridge/*, so the fix is the driver for this bump.
# Also in range: 0.8.0 made the delta log append-only and added conversion
# `provenance`; 0.9.0 anchored the Index's urn:air: identifiers and added the
# /agents/search fan-out hop to sm-bridge's OWN gateway; 0.10.0 added an
# `is_listed` hook to that gateway.
# Orrery is unaffected by all three of 0.9.0's breaking changes, verified rather
# than assumed: it does not read the `synthesized` extension field (removed), does
# not mount sm-bridge's gateway at all (so the A2A card's `_meta.identifier` change
# cannot reach it — server/routes/identity.py serves this org's catalog and card
# surfaces itself), and passes member ids rather than URNs to resolve (so the
# non-lower-case `URN:` now 400ing where it used to 404 is unreachable from here).
# NOT adopting sm-bridge's gateway or its new `is_listed` hook: _gated_catalog_entries
# distinguishes OMITTED from WITHHELD, applies the resolvable-card rule and caps at
# AGENT_SEARCH_LIMIT. A boolean predicate cannot express that, and folding the two
# counts together is exactly what that code refuses to do.
# The >=0.4.1 FLOOR in pyproject.toml is deliberately NOT raised: every symbol
# Orrery imports exists in 0.4.1 with an identical shape (verified by
# introspection across both wheels), so 0.4.1 remains the honest minimum API.
# The lockfiles are what CI and the image install; the floor states a requirement.
# NOT taking [feed]: it hash-chains the delta log for COMPLETENESS, but Orrery's
# DeltaStore is in-memory and reseeds from a wall-clock base_seq on every restart
# (_monotonic_base_seq) — deliberately gapped. A completeness-verifiable
# feed over an intentionally gapped log would either false-alarm every restart or
# claim a guarantee the store cannot honour.
#
# ⚠️ THIS REFUSAL STILL STANDS, AND IT IS NOT ABOUT THE FEDERATION FEED. Since
# the intelligence-feed work this org runs TWO logs, and the next reader will otherwise conclude
# the refusal was reversed:
#
#   * sm-bridge's MEMBER-DELTA store — this one. In-memory, reseeded from a wall
#     clock on every restart, DELIBERATELY GAPPED. Its contract is a monotonic
#     sequence, not a gapless one, so gaps between bases are correct there. It
#     must NOT be hash-chained, and [feed] is still refused.
#   * the sm-federation §4 INTELLIGENCE feed — a different payload (aggregate
#     intelligence envelopes, not member deltas), a different store
#     (public.federation_feed_entries, durable and append-only) and a different
#     contract (gapless, chained, and a restart that reseeded it would be
#     detectable as head_rewind rather than silent). server/federation_feed.py.
#
# The distinction matters because the reasoning here was overgeneralised once
# already: that change's report and conformance/federation/claims.json both cited
# THIS note as evidence that Orrery could not have a completeness-verifiable feed
# AT ALL. It never said that. It said this store cannot back one.
